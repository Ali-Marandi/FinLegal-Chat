# FinLegal-Chat v0.2.0 GitHub Actions Signing and Release Guide

## Recommended release flow

The repository workflow at `.github/workflows/release-v020.yml` builds Linux, Windows, and macOS artifacts in separate native runners. A tag such as `v0.2.0` or a manually dispatched version starts the matrix. Each build updates the package version locally, runs the platform-specific electron-builder target, uploads the artifacts, and passes them to a final release job. The release job creates the GitHub release if it does not exist or uploads replacement assets if the tag already exists.

The workflow intentionally fails closed when a platform build or expected installer is missing. A GitHub Actions release should be created only from a reviewed commit and a protected tag.

## Required repository secrets

| Secret | Platform | Purpose |
|---|---|---|
| `WINDOWS_CERTIFICATE_BASE64` | Windows | Base64-encoded Authenticode code-signing certificate, normally a `.pfx`. |
| `WINDOWS_CERTIFICATE_PASSWORD` | Windows | Password for the PFX. |
| `MACOS_CERTIFICATE_BASE64` | macOS | Base64-encoded Developer ID Application certificate exported as `.p12`. |
| `MACOS_CERTIFICATE_PASSWORD` | macOS | Password for the `.p12`. |
| `APPLE_ID` | macOS | Apple Developer account email used for notarization. |
| `APPLE_APP_SPECIFIC_PASSWORD` | macOS | App-specific password used for notarization. |
| `APPLE_TEAM_ID` | macOS | Apple Developer Team ID. |

Do not commit certificates, private keys, passwords, provisioning files, or notarization credentials. Store them as repository or environment secrets, preferably in a protected `release` environment requiring reviewer approval. Rotate certificates and app-specific passwords according to the organization’s key-management policy.

## Certificate preparation

For Windows, obtain an Authenticode certificate from the organization’s approved certificate authority, export the certificate and private key as a password-protected PFX, and base64-encode the file without line wrapping. The workflow passes the encoded value through `WIN_CSC_LINK` and the password through `WIN_CSC_KEY_PASSWORD`; electron-builder uses those values to sign the Windows installer and application binaries.

For macOS, enroll in the Apple Developer Program, create a **Developer ID Application** certificate, export it as a password-protected `.p12`, and base64-encode it without line wrapping. Enable hardened runtime in the electron-builder configuration. Provide the Apple ID, app-specific password, and Team ID so electron-builder can submit the signed application for notarization. The release should not be advertised as notarized unless the notarization step completes successfully.

## Suggested local preparation commands

Run these commands on a trusted workstation, not in a public log. Replace the file names locally and never paste the output into source control.

```bash
base64 -w 0 FinLegal-Chat-Developer-ID.p12 > macos-cert.b64
base64 -w 0 FinLegal-Chat-Authenticode.pfx > windows-cert.b64
```

Then create the corresponding GitHub Actions secrets using the repository Settings → Secrets and variables → Actions interface. A cloud HSM, certificate manager, or organization signing service may be preferable for a production program; the PFX/P12 secret approach is the simplest initial implementation.

## Workflow setup and release controls

Protect the default branch and require pull requests for workflow changes. Restrict who can create `v*.*.*` tags or approve the release environment. Review the effective electron-builder configuration, dependency lockfile, release notes, and artifact names before publishing.

The v0.2.0 workflow supports both tag-triggered and manual releases. The tag path is preferred for a traceable release: merge the reviewed commit, create and push `v0.2.0`, wait for all three platform jobs, then verify the release assets and signatures. A manual dispatch is useful for rehearsals and test releases, but production policy should require an approved version and release reviewer.

## Verification checklist

| Check | Windows | macOS | Linux |
|---|---:|---:|---:|
| Installer produced | NSIS `.exe` exists. | `.dmg` exists. | AppImage and `.deb` exist. |
| Signature | Inspect Authenticode signature and publisher. | Inspect Developer ID signature and hardened runtime. | Verify SHA-256 checksum; Linux package signing can be added separately. |
| Notarization | Not applicable. | Verify Apple notarization/staple status. | Not applicable. |
| Clean install | Install on a clean supported runner or VM. | Install on a supported clean macOS host. | Install AppImage and `.deb` on supported Linux. |
| Launch smoke test | Open workspace, navigate, select a file, and verify local persistence. | Same. | Same. |
| Release asset | Confirm exact version, architecture, and checksum. | Confirm exact version, architecture, and checksum. | Confirm exact version, architecture, and checksum. |

## Important limitations of the current workflow

The macOS job targets `macos-13`, which produces an Intel-compatible x64 build. If Apple Silicon support is required, add a separate `macos-14` arm64 job or adopt a universal build process and test both architectures. The current desktop preview also uses a default Electron icon and does not yet integrate production backend AI orchestration, enterprise SSO, or customer-managed key infrastructure. Those should be addressed before positioning v0.2.0 as a production financial-enterprise release.
